## Golden pattern from the DNA-computing project

Pull real data → run analysis/model → write pytest assertions on the result, not print statements. Assert *relationships* between values, not just absolute numbers (e.g. `assert end_mfe < internal_mfe`), and double-check the direction of the relationship before asserting it — the DNA project's known trap was an MFE sign error (more negative = stronger binding). The equivalent traps here: Kepler flux dips are a *decrease*, LIGO significance should be higher *inside* the event window than outside it, orbital semi-major axes should stay *within* bounds not just below/above one.

Loop mechanics: fixed spin a=0.9M, prograde equatorial, matching 3b. Each iteration scores the current b (`score = |r_min - target|`, or a fixed penalty of 50 if b ≤ b_crit and the photon is captured), then asks the local model — via an Ollama tool-call schema (`propose_impact_parameter(b, reasoning)`) — to reason over the full JSON history and propose the next b to try. Ollama 0.32.3 with this model doesn't reliably populate the native `tool_calls` field even though it advertises the capability — it often returns the tool-call JSON as plain `content` text instead — so added a fallback parser (direct JSON parse, then regex-extracted JSON blob, then a last-resort regex for a bare `b: <number>`).

Hit a real reliability problem worth flagging for any future session that puts a small local model in a control loop: an early version blindly used whatever the model (or parse-failure fallback) proposed as the next point to try, and it wasn't a safe assumption — one run had the model propose the same b back for several iterations straight (arguably reasonable "already close enough" behavior, harmless), but a plain pytest run of the same code produced a case where the score never improved across all 4 iterations at all, failing the improvement assertion. Since scoring a candidate b is free (pure root-finding, no real experiment), fixed this by turning the decision step into a guarded choice rather than blind trust: every iteration evaluates three candidates — the LLM's proposed b, a numeric fallback (a fixed 13-15% step toward the target from the best valid point seen so far, direction chosen from the known monotonic relationship), and simply staying at the current b — and commits to whichever actually scores best. This is this session's equivalent of the DNA-computing project's MFE-sign trap, restated for an agentic loop: it's not enough to log what the model said, you have to check the direction of the outcome actually helped before trusting it. Re-ran the full standalone script after the fix (8 iterations, ~140s wall time, dominated by 3B-model inference at roughly 10-30s/call on this laptop's CPU): converged score 1.44 → 0.54 → 0.22 then held, log (`kerr_agent_loop_log.json`) shows the guard genuinely doing work across the run — iteration 1 used the LLM's own proposal (5.0, real improvement), iteration 2 used the numeric fallback (LLM's suggestion was worse), iterations 3+ mostly held status quo, including one case where the LLM explicitly (and correctly) reasoned "already close, moving further would likely increase the penalty of capture" but its own proposed number would in fact have scored slightly worse and was rejected by the guard anyway. `test_kerr_agent_loop.py` runs a shorter 4-iteration version from a deliberately bad, deterministic starting point (b=10.0, score 4.49) rather than the standalone script's true `randomize parameters` start, so the improvement assertion is reliable rather than dependent on where a random draw happens to land — asserts the best score found strictly beats the initial score, that the winning entry is never a captured/invalid trajectory, and that all proposed b stayed within the declared search bracket. Session's equivalent of the MFE-sign trap: same direction-of-capture check as 3a (`is_captured` just inside vs. just outside b_crit) but run on *both* branches, since prograde/retrograde have oppositely-signed b_crit — easy to get backwards. Photon trajectory integration was the hard part: naively integrating the affine-parameter ODE with a sign-flipping sqrt(R) term either hit floating-point step-size collapse right at the horizon (Boyer-Lindquist coordinates are singular there — dφ/dλ has an explicit 1/Δ term that blows up, a real coordinate pathology, not a bug) or stalled indefinitely approaching a scattering turning point (dr/dλ→0 continuously, so the turning-point event never registers a clean sign crossing). Fixed both: stop just outside the horizon (r_+ × 1.05) rather than exactly at it, and pre-locate each turning point analytically via `brentq` on R(r,b)=0 before integrating, then hard-stop at r_min×1.02 and restart the ODE with the sign flipped for the outbound leg. Hit one real bug along the way worth flagging for future sessions: R(r,b)=0 has multiple roots for large b (the cubic-in-r factor), and picking the *first* sign change scanning outward from the horizon grabbed a spurious inner root instead of the actual (larger-r, physically-reached) turning point — silently produced a captured=False trajectory that never actually turned around and ran to the integrator's step budget. Fixed by taking the outermost (largest-r) root instead, i.e. the first one the inbound photon actually reaches.
